Data Generation & Agentic RL for Seed Models

为 Coding Agent 构建训练轨迹Building Training Trajectories for Coding AgentsCoding Agentの学習軌跡を構築する

一个能用的产物，未必对应一条适合训练的轨迹。围绕多维表格搭建任务，我们把模型决策、工具调用和真实返回一起记录，比较 Spec 规划、在线纠偏与离线编辑，寻找质量与生成成本之间的取舍。A usable artifact does not always come from a trajectory worth training on. In tasks that build database applications, we record model decisions, tool calls, and actual results together, then compare Spec-guided planning, online correction, and offline editing to understand their quality–cost trade-offs.使える成果物が得られても、その軌跡が学習に適しているとは限らない。データベースアプリの構築を題材に、モデルの判断・ツール呼び出し・実際の返り値を記録し、Specによる計画、オンライン修正、オフライン編集の品質と生成コストを比較する。

任务从用户需求开始，涉及表、视图、仪表盘、工作流和权限。Seed 在 Harness 中读取技能、编写参数或脚本、调用 CLI；工具返回进入下一轮上下文。训练数据需要保留这条决策与执行的因果链。Tasks begin with a user request and span tables, views, dashboards, workflows, and permissions. Inside the harness, Seed reads skills, writes parameters or scripts, and invokes the CLI. Tool results become context for the next turn. Training data needs to preserve this causal chain of decisions and execution.ユーザーの要件から始め、テーブル、ビュー、ダッシュボード、ワークフロー、権限を構築する。Harness内でSeedがスキルを読み、引数やスクリプトを書き、CLIを実行する。ツールの返り値は次のターンの文脈となる。この判断と実行の因果関係を学習データに残す。

Harness 如何承载一条轨迹How the Harness carries a trajectoryHarness が軌跡を支える仕組み

Online 生成与修复共用执行底座One runtime for Online generation and repairOnline の生成と修復を支える共通実行基盤

Online 包含首次生成、运行时纠偏和评审后的有界重生成；教师监督覆盖每一次执行。这些执行共用同一个 Harness：上下文组装、工具环境、真实回执和检查点。Spec→TodoList 位于规划层，计划指导执行，问题归因更新计划。Offline 接收无需继续重生成的完整轨迹，沿依赖做编辑与核验；发现当前问题需要真实执行时，携问题与证据回流 Online。Online includes initial generation, runtime correction, and bounded regeneration after review; teacher supervision covers each execution. They share one Harness for context assembly, tool environments, actual receipts, and checkpoints. Spec→TodoList provides the planning layer: plans guide execution and attribution updates them. Offline receives complete trajectories that need no further regeneration, edits and verifies dependencies, and returns an issue with evidence to Online when real execution is required.Onlineは初回生成、実行中の修正、評価後の回数制限付き再生成を含み、教師の監督が各実行をカバーする。これらは1つのHarnessで文脈の構築、ツール環境、実際の返却値、チェックポイントを共有する。Spec→TodoListは計画層にあり、計画が実行を導き、原因分析が計画を更新する。Offlineは追加の再生成が不要な完全な軌跡を受け取り、依存関係に沿って編集・検証する。実行が必要な問題は証拠とともにOnlineへ戻す。

例如，一条工作流依赖尚未创建的字段：TodoList 应先安排字段创建，再安排工作流；Harness 执行后把真实字段 ID 和返回写入轨迹；Online 在错误决策前恢复可继续执行的上下文与环境，再生成受影响后缀。若只需删除一次无副作用的失败调用并调整后文，Offline 可在核验依赖后局部编辑。涉及状态或返回值变化时，必须有对应的真实执行证据。For example, a workflow may depend on a field that has not been created. TodoList should schedule field creation first; the Harness records the actual field ID and tool response. Online restores a runnable context and environment before the mistaken decision, then regenerates the affected suffix. If the change only removes a failed call with no side effects and adjusts later wording, Offline can edit locally after checking dependencies. Changes to state or returned values require corresponding execution evidence.たとえば、未作成のフィールドにワークフローが依存している場合、TodoList はフィールド作成を先に置く。Harness は実際のフィールド ID と返却値を軌跡に記録する。Online は誤った判断の直前に実行可能な文脈と環境を復元し、影響する後続部分を再生成する。副作用のない失敗呼び出しの削除と後文の調整だけなら、Offline で依存関係を確認して局所編集できる。状態や返却値を変える場合には、対応する実行証拠が必要になる。

抽象轨迹模型Abstract trajectory model抽象的な軌跡モデル

抽象地看，每一轮都把历史消息与当前环境交给模型，由模型选择动作；Harness 执行工具并回填真实返回，形成下一轮状态。失败时保留回执与成本，在检查点恢复上下文和环境，再选择新的动作。At an abstract level, each step gives the model its message history and current environment. The model selects an action; the Harness executes the tool and appends the actual result to form the next state. A failure keeps its receipt and cost, restores context and environment at a checkpoint, and then selects a new action.抽象的には、各ターンでメッセージ履歴と現在の環境をモデルに渡し、モデルが動作を選ぶ。Harnessがツールを実行して実際の返却値を追加し、次の状態を作る。失敗時も返却値とコストを残し、チェックポイントで文脈と環境を復元してから新しい動作を選ぶ。

Online：在错误发生处修复Online: repair where the error occursOnline：誤りが生じた位置で修復する

能力边界问题先检查是否存在保留全部明确要求的等价改写，通过后才从头生成，并继续按原始需求评审。网络、认证等环境故障单独记录。交接给 Offline 的是无需继续重生成的轨迹，以及原 Query、真实回执、评审和修复记录。Capability limits first require an independent check that an equivalent rewrite preserves every explicit requirement. 定向指导减少了重复尝试，但收益要沿具体行为核验：代码组的 5 个目标错误，在原轨迹后段都已经自行修复；指导避免了重犯，其中 4 条仍出现其他参数错误。语义组补好了部分公式和字段，也留下了筛选与余额口径问题。Guidance reduced repeated attempts, but its effect needs to be checked against actual behavior. Semantic repairs restored some formulas and fields, but left filtering and balance-definition problems.指示は試行の繰り返しを減らしたが、効果は実際の行動で確かめる必要がある。コードの対象エラー5件は、元の軌跡でも後続で自己修正されていた。指示により再発を防げた一方、4件では別の引数エラーが発生した。意味上の修復では一部の式やフィールドを補えたが、絞り込みと残高定義の問題が残った。

另一个影响读数的因素是问题匹配：同一缺陷可能被三轮 Judge 写成不同描述，拆成单票后漏计。因此表中的小幅分差不作为稳定提质的证据；更少的生成 token 也需与功能保留一起检查。Issue matching also affected the readings: the same defect could receive different descriptions across judges, split into single-vote clusters, and be missed. The small score differences therefore do not establish a stable quality gain. Lower generation tokens also need to be checked alongside preservation of functionality.問題の対応付けも測定に影響した。同じ欠陥がJudgeごとに異なる表現となり、1票ずつの別クラスタに分かれて計上されないことがあった。このため小さな点差から安定した品質向上とは判断しない。生成tokenの削減も、機能が維持されたかと併せて確認する。

Offline：沿依赖关系编辑Offline: edit along dependenciesOffline：依存関係に沿って編集する

Offline 的处理对象是一条已有的完整轨迹。先确定修改会影响哪些资源状态、返回值、控制条件和文字上下文，再选择单 turn 编辑、有限片段编辑或不编辑。四类依赖可以重叠；需要真实执行的问题回流 Online，未知依赖或其他准出失败进入 Pending。Offline starts from an existing complete trajectory. It identifies affected resource states, returned values, control conditions, and textual context, then chooses a single-turn edit, a bounded segment edit, or no edit. The four dependency types can overlap. Issues requiring real execution return to Online; unknown dependencies and other release failures enter Pending.Offlineは既存の完全な軌跡を起点とする。影響を受けるリソース状態、返却値、制御条件、文章文脈を確認し、単一ターン編集、限定区間編集、編集なしから選ぶ。4種類の依存関係は重なり得る。実行が必要な問題はOnlineへ戻し、依存関係不明やその他の受け入れ失敗はPendingに置く。

例如，删除一个无副作用的失败调用后，后文的“刚才失败，所以重试”也需要重写；若修改字段创建参数，后续使用的字段 ID、公式和视图也可能受影响。动作变化必须有相应的真实执行证据，不能把失败回执改成成功。清洗同样保留信息时序，不把事后知道的结论提前写入决策。For example, deleting a failed call with no side effects also requires rewriting later statements such as “that failed, so retry.” Changing field-creation arguments may affect field IDs, formulas, and views downstream. Action changes require matching real execution evidence; a failed result cannot simply be rewritten as success. Cleaning preserves information order rather than inserting later knowledge into earlier decisions.例えば副作用のない失敗呼び出しを削除した場合、後の「失敗したので再試行する」という記述も直す必要がある。フィールド作成の引数を変えれば、後続のID、数式、ビューにも影響し得る。操作の変更には対応する実行証拠が必要で、失敗結果を成功に書き換えることはできない。クリーニングでも情報の順序を保ち、後から得た知識を過去の判断に挿入しない。

从轨迹到训练样本From trajectories to training examples軌跡から学習サンプルへ

当前准出规则按问题多数票计算分档：有严重问题为 2 分，仅轻微问题为 3 分，无问题为 4 分；无问题且至少两轮效率评审为 high 时为 5 分。4/5 分轨迹再通过真实性与格式检查。评分、产物验收和训练格式承担不同检查职责。The current release rubric aggregates issue-level majority votes: severe issues yield 2, minor-only issues yield 3, and no issues yield 4. An issue-free trajectory earns 5 when at least two efficiency reviews rate it high. Scores 4/5 then require authenticity and format checks. Scoring, artifact acceptance, and training-format validation serve different purposes.現在の受け入れ基準は問題単位の多数決で段階を決める。重大な問題があれば2、軽微のみなら3、問題がなければ4。問題がなく、効率評価が2回以上highなら5となる。4/5点の軌跡にも真正性と形式の確認を行う。スコア、成果物の検収、学習形式の検証はそれぞれ役割が異なる。

一批已提交训练的数据包含 207 条轨迹、206 个 Query 组，按 Query 分组拆为 186 条训练与 21 条独立测试。训练侧展开为 5,458 个 assistant 目标：每个目标保留完整、未截断的历史上下文，原生思考只保留当前目标轮。测试数据不提交训练或选 checkpoint。One submitted training dataset contains 207 trajectories across 206 Query groups, split by Query into 186 training and 21 independent test trajectories. Training expands into 5,458 assistant targets. Each target retains the complete, untruncated conversation history, with native reasoning kept only for the target turn. Test data is not submitted for training or checkpoint selection.提出済みの学習データは207軌跡、206のQueryグループを含む。Query単位で186軌跡を学習、21軌跡を独立テストに分けた。学習側は5,458のassistantターゲットに展開し、各ターゲットには切り詰めていない全履歴を保持する。ネイティブの推論は対象ターンのみ残し、テストデータを学習やcheckpoint選択に提出しない。

新一轮在线对照从同一 Query 各自 fresh 生成：普通生成，对比教师纠偏及后验修复，先检查 10 对再扩到 100 对。这样可以把重新生成本身的收益，与修复机制的收益分开。接下来的判断标准是：同一需求上的功能保留、可用轨迹比例，以及包含教师和 Judge 的完整成本。The next online comparison starts fresh from the same Query in each arm: ordinary generation versus teacher correction and post-trajectory repair, checking ten pairs before expanding to one hundred. This separates the benefit of regeneration itself from the repair mechanism. 方案设计：Spec → TodoListDesign: Spec → TodoList設計：Spec → TodoList

规划工具与普通执行工具共用 Harness 的调用、回执与记录机制。执行返回推动 TodoList 状态更新；Judge–Fix 的归因推动计划修订。需要重新执行的修改进入 Online；已有轨迹中可验证的局部修改按 Offline 处理。TodoList 的完成标记始终要能追到真实动作与回执。The planning tool shares the Harness’s call, receipt, and recording mechanism with execution tools. Tool results update TodoList state; Judge–Fix findings drive plan revisions. Changes requiring new execution go through Online; verifiable local changes to an existing trajectory follow Offline. TodoList completion marks must remain traceable to actual actions and receipts.計画ツールも通常の実行ツールも、Harness の呼び出し・返却・記録の仕組みを共有する。実行結果で TodoList の状態を更新し、Judge–Fix の原因分析で計画を改訂する。再実行が必要な変更は Online、既存軌跡内の検証可能な局所変更は Offline として扱う。TodoList の完了印は、実際の動作と返却値までたどれる必要がある。

Spec 提供业务对象、约束和依赖，TodoList 将其组织成可更新的执行计划。规划工具维护任务顺序、完成状态和执行依据，让计划随真实工具返回更新。这是本方案采用的规划结构；前面的三组实验比较的是 Spec 的输入位置。Specs provide business objects, constraints, and dependencies; a TodoList organizes them into an updatable execution plan. The planning tool tracks task order, completion status, and execution evidence, updating the plan as actual tool results arrive. This is the planning structure adopted in our design; the three-arm experiment above compared where to place the Spec.Specが業務オブジェクト・制約・依存関係を定義し、TodoListが更新可能な実行計画にまとめる。計画ツールでタスクの順序、完了状態、実行の根拠を管理し、実際のツールの返り値に応じて計画を更新する。これが本設計で採用する計画構造であり、先の3条件の実験ではSpecの入力位置を比較した。

Judge–Fix 将同时检查计划、实际动作及二者的一致性。例如，工作流依赖的字段尚未建立，就修正 TodoList 的前置任务和执行顺序，并重新生成受影响的执行片段。保留计划修订、工具调用与真实回执，经核验后形成显式规划与执行的训练数据。Judge–Fix would assess the plan, actual actions, and their consistency. If a workflow needs a field that has not yet been created, for example, the repair would revise the TodoList’s prerequisites and task order, then regenerate the affected execution segment. Plan revisions, tool calls, and actual results would be retained and verified as training data for explicit planning and execution.Judge–Fixは計画、実際の操作、両者の整合性を評価する設計とする。例えば、ワークフローが依存するフィールドがまだ作られていなければ、TodoListの前提タスクと実行順序を修正し、影響を受ける実行区間を再生成する。計画の修訂、ツール呼び出し、実際の返り値を保存・検証し、明示的な計画と実行の学習データにする。

验收仍以原始 Query 为准。模型生成的 Spec 和 TodoList 保留为可修订的计划及过程证据，不新增用户要求；完成标记需要对应实际执行。对照实验将比较有无 TodoList 时的任务完成率、依赖与顺序错误、可用轨迹比例及完整成本。这条设计的收益待后续实验验证。Acceptance would remain anchored to the original Query. Model-generated Specs and TodoLists would be revisable plans and process evidence, without adding user requirements; completion marks would need to reflect actual execution. A controlled comparison with and without a TodoList would measure task completion, dependency and ordering errors, usable-trajectory yield, and full cost. The benefits of this design remain to be tested.受け入れ基準は引き続き元のQueryとする。モデルが生成したSpecとTodoListは修正可能な計画および過程の証拠として残し、ユーザー要件を追加しない。完了の印には実際の実行が対応する必要がある。TodoListの有無を比較し、タスク完了率、依存関係や順序の誤り、利用可能な軌跡の割合、全コストを測る。この設計の効果は今後の実験で検証する。
