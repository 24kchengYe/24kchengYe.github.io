用评审反馈修复 SpecRepairing Specs with Feedback評価フィードバックでSpecを修復する

2026 年 6—10 月June–October 20262026年6–10月

用户要求统计培训完成度，设计里也有一个同名进度字段，但没有写明怎样从培训记录计算。管理员原本可以维护业务数据，修复后却变成只读。这两种设计都曾通过文档检查，直到执行建表后才暴露问题。A user asked to track training completion. The design included a progress field with the right name, but never explained how to calculate it from training records. In another case, an administrator who could maintain business data became read-only after repair. Both designs passed document checks; their problems surfaced only after the applications were built.研修の完了率を集計する要求に対し、設計には同名の進捗フィールドがあっても、研修記録からの計算方法がなかった。別の例では、業務データを管理できた管理者が修復後に読み取り専用になった。どちらも文書審査を通過し、実際に構築して初めて問題が現れた。

Judge–Fix 要解决的就是这类错误：Judge 找出设计缺口，Fix 修改文档，Router 决定先修哪个业务域。项目还尝试了 Verifier，在写回之前比较修前、修后两份文档，判断这次修改是否应该接受。Judge–Fix addresses these failures: Judge identifies design gaps, Fix edits the document, and Router chooses which domain to repair first. We also tried a Verifier that compares the before-and-after documents and decides whether to accept an edit before writing it back.Judge–Fixはこうした誤りを扱う。Judgeが設計の不足を指摘し、Fixが文書を修正し、Routerが修復する領域の順序を決める。書き戻す前に修復前後の文書を比較し、変更を採用するか判断するVerifierも試した。

几个月的实验没有得到“检查越多、修得越好”的结果。限制无关修改有过明确收益；增加候选、投票和修复轮数则经常只增加成本。判断一个改动是否值得保留，需要看原问题有没有解决，也需要看原来的业务还能不能完成。Across several months of experiments, more checks did not consistently produce better repairs. Restricting unrelated edits helped; adding candidates, votes, or repair rounds often just added cost. A useful change must resolve the original problem while preserving the original task.数か月の実験では、確認を増やすほど修復が良くなるとは限らなかった。無関係な変更の制限には効果があったが、候補、投票、修復回数の追加は費用だけを増やすことも多かった。元の問題を解消し、元の業務も実行できることが採用条件となる。

先修依赖，再修下游Repair dependencies before downstream design依存関係を先に修復する

多维表格设计分为数据表、仪表盘、工作流和权限四个域。后三域依赖表和字段，因此不能把四份错误清单各自交给模型，最后拼起来。例如统计图和工作流同时缺一个字段，应先补表，再修改两个下游设计。A Bitable design has four domains: tables, dashboards, workflows, and permissions. The latter three depend on tables and fields, so four independent error lists cannot simply be repaired and stitched together. If a chart and a workflow both lack the same field, repair the table first, then update both consumers.多次元テーブルの設計は、テーブル、ダッシュボード、ワークフロー、権限の四領域に分かれる。後ろの三領域はテーブルとフィールドに依存するため、別々のエラー一覧を修復して結合するだけでは足りない。グラフとワークフローが同じフィールドを必要とするなら、まずテーブルを補い、その後で両方を修正する。

主链路先检查四域，由 Router 选择修复位置。修改后重新检查；普通阶段未解决的样本可以进入难例阶段，但总预算有限。最后对同一份文档投票，确认业务通过后再处理格式。格式候选如果改变了文档，也需要重新确认业务判断。The main pipeline checks all four domains, lets Router choose a repair location, then checks the revised document again. Unresolved cases can move from the regular stage to a hard-case stage within a bounded budget. Finally, votes on the same document confirm semantic acceptance before formatting. If a formatting candidate changes the document, its semantics must be checked again.主処理は四領域を審査し、Routerが修復箇所を選び、修正後に再審査する。通常段階で解決しない例は難例段階へ進めるが、総予算には上限がある。最後に同一文書への投票で業務要件の合格を確認し、形式を整える。形式修正で文書が変われば、業務面も再確認する。

这些流程不是所有历史实验的统一配置。图展示的是 2026-10-16 收录的本地实现，具体实验仍按各自冻结参数比较。The diagram shows the local implementation recorded on October 16, 2026. Historical experiments used their own frozen settings rather than one universal pipeline configuration.図は2026年10月16日に収録したローカル実装を示す。過去の実験はすべて同じ設定ではなく、それぞれ固定したパラメータで比較する。

一次修复包含什么What a repair contains一回の修復で行うこと

Fix 读取用户需求、当前设计和待修问题。对 Markdown SpecDoc，它主要生成局部补丁；对 HostPlan，则按 JSON 结构写回。程序先确认输出能解析、补丁能应用，才把候选送去评审。原文没匹配上，不能算作修复已完成。Fix reads the user requirements, current design, and outstanding issues. It mainly produces local patches for Markdown SpecDocs and writes structured JSON for HostPlan. A candidate is reviewed only after its output parses and its patch applies. A patch that cannot match the original text is not a completed repair.Fixはユーザー要求、現在の設計、未解決の問題を読む。Markdown SpecDocでは主に局所パッチを作り、HostPlanではJSON構造で書き戻す。出力を解析でき、パッチを適用できた候補だけを審査する。元の文面に一致しないパッチは、修復完了とは扱わない。

每轮候选从同一个输入版本生成，分别检查、择优接纳，不把不同候选直接拼接。候选被拒绝时保留旧文档，下一轮接收失败原因。局部通过后，还要返回主链路做整体检查。Candidates in a round start from the same input version. They are checked separately and accepted by comparison, not spliced together. Rejection preserves the old document and sends the failure reason to the next round. A locally accepted repair still returns to the main pipeline for an overall check.同じラウンドの候補は同一の入力版から生成する。個別に審査して比較採用し、異なる候補を直接つなぎ合わせない。却下時は元の文書を保持し、失敗理由を次のラウンドへ渡す。局所的に合格しても、主処理に戻して全体を確認する。

局部补丁、输出恢复、对象替换、候选去重和回退都已有实现。后续发现同类错误，应查它在哪个入口失效，而不是再加一层同名机制。Local patches, output recovery, object replacement, candidate deduplication, and fallback already exist. When a similar failure recurs, trace where the existing mechanism failed before adding another layer.局所パッチ、出力復旧、オブジェクト置換、候補重複排除、フォールバックは実装済みである。同類の失敗が起きたら、同名の仕組みを追加する前に既存の入口のどこで機能しなかったかを調べる。

少改一些，确实有用Smaller edits helped変更を絞る効果

6 月的 Non-Table 对照固定了同一批 300 条输入。仅增加能力说明，Fix 阶段通过数从 156 变为 154；进一步要求保留合格段落、只修改问题及必要依赖后，通过数达到 177，已合格域的退化次数从 76 降到 47。另一组 Table 对照都是 179/300，未出现同样提升。June’s Non-Table comparison used the same 300 inputs. Adding capability descriptions alone changed Fix-stage passes from 156 to 154. Requiring preservation of valid sections and limiting edits to issues and necessary dependencies raised passes to 177 and reduced regressions in already-passing domains from 76 to 47. A separate Table comparison stayed at 179/300 in both arms.6月のNon-Table比較は同じ300件の入力を固定した。機能説明の追加だけではFix段階の合格数は156から154になった。合格済みの段落を保持し、問題と必要な依存関係だけを修正する条件を加えると177件になり、合格済み領域の退化は76回から47回に減った。別のTable比較は両群とも179/300で、同じ改善はなかった。

保留下来的做法是限制无关修改，不是禁止修改所有旧内容。若工作流缺少必要字段，只保护旧表、不允许补字段，同样修不好。We retained the restriction on unrelated edits, not a blanket ban on editing old content. A workflow missing a required field cannot be fixed if the old table is protected against every addition.残したのは無関係な変更の制限であり、既存部分をすべて変更禁止にする方針ではない。ワークフローに必要なフィールドがないとき、古いテーブルを保護して追加まで禁じれば修復できない。

另一组 8 个工作流难例更直接：原文补丁准出 3 条，换成对象 ID 加文档哈希后只有 1 条；保留原补丁，只明确流程分支范围、首次命中和完成状态来源，准出 7 条。新定位协议拒绝了大量候选。定位更稳定是设计目标，并不等于整链结果更好。Eight hard workflow cases made the trade-off clearer. Original-text patches accepted three cases; replacing them with object IDs and document hashes accepted only one. Keeping the original patch protocol but clarifying branch scope, first-match behavior, and the source of completion status accepted seven. The new addressing protocol rejected many candidates: more stable targeting did not translate into better end-to-end results.ワークフローの難例8件では差がより明確だった。原文パッチの准出は3件、オブジェクトIDと文書ハッシュへの変更後は1件だった。元のパッチを保ち、分岐の範囲、最初の一致、完了状態の出所だけを明確にすると7件になった。新しい位置指定方式は多くの候補を却下した。位置の安定性という設計目標が、そのままチェーン全体の改善になるわけではない。

扩大预算也未必有用。17 条难例从五轮增加到七轮，准出仍为 13 条，token 从 44.57M 增至 53.11M。上述结果来自不同样本集，不能把它们的绝对通过率排列成一条提升曲线。More budget also failed to guarantee improvement. Expanding 17 hard cases from five to seven rounds left acceptance at 13 while tokens rose from 44.57M to 53.11M. These experiments use different samples; their absolute pass rates are not points on one improvement curve.予算を増やしても改善するとは限らない。難例17件を5回から7回に増やしても准出は13件のまま、トークンは44.57Mから53.11Mに増えた。これらは異なる標本の結果なので、絶対合格率を一本の改善曲線として並べることはできない。

重复判断解决不了所有错误Repeated judgments cannot fix every error判断の繰り返しで直せない誤り

同一文档重复检查会得到不同结果。6,457 条 SpecDoc 曾在链内通过 6,291 条，单次独立重判只通过 5,315 条。这推动了同版本多数投票：最多三票，至少两票通过；结论已确定就不再凑满票数。Repeated checks of one document can disagree. Of 6,457 SpecDocs, 6,291 had passed inside the pipeline, but only 5,315 passed a single independent reassessment. This motivated majority voting on the same version: at most three votes, at least two passes, stopping as soon as the outcome is determined.同じ文書を繰り返し審査しても結果は揺れる。6,457件のSpecDocはチェーン内で6,291件が合格したが、独立した単回再審査では5,315件だった。そこで同一版への多数決を導入した。最大3票、2票以上で合格とし、結論が決まった時点で打ち切る。

固定已有票据的回放中，早停和有效首票复用让 146 个节点的调用从 2,442 次降至 2,190 次，结果相同。但在线重新采样时还有限流、重试和延迟，一次耗时对照只缩短约 0.66%。不能用离线调用节省比例代替实际加速。A replay with fixed recorded votes reduced calls across 146 nodes from 2,442 to 2,190 through early stopping and reuse of valid first votes, with identical outcomes. Online sampling also involves rate limits, retries, and latency: one timing comparison improved by only about 0.66%. Saved replay calls are not equivalent to measured wall-clock speedup.既存の票を固定したリプレイでは、早期停止と有効な初回票の再利用により、146ノードの呼び出しが2,442回から2,190回へ減り、結果は同じだった。オンライン再生成には制限、再試行、遅延もあるため、ある実測比較での時間短縮は約0.66%にとどまった。リプレイでの呼び出し削減率を実際の高速化率とは扱えない。

投票主要减少随机翻转。Verifier 的 H002 错误图表连续三次被接受，H003 正确日期修改连续三次被暂缓，重复判断没有纠正它们。此时要改的是判断依据。Voting mainly reduces random flips. Verifier accepted H002’s incorrect chart three times in a row and deferred H003’s correct date edit three times. Repetition did not fix either mistake; their judgment criteria need attention.投票が主に減らすのはランダムな反転である。VerifierはH002の誤ったグラフを3回連続で採用し、H003の正しい日付変更を3回連続で保留した。繰り返しでは直らず、判断根拠を見直す必要がある。

Verifier 卡在了哪里Where the Verifier stalledVerifierが停滞した理由

Verifier 比较的不只是两个分数。它先列出当前问题，再确认候选是否修好了目标、保留了需求、没有破坏别处。只有这些条件满足，连续评分才用于比较候选；高分不能抵消删除需求或权限退化。Verifier does more than compare two scores. It enumerates current problems, then checks whether a candidate fixes the target, preserves requirements, and avoids damage elsewhere. Continuous scores rank candidates only after these conditions hold; high scores cannot compensate for deleted requirements or degraded permissions.Verifierは二つの点数を比較するだけではない。まず現在の問題を列挙し、候補が対象を修復し、要求を保持し、他所を壊していないかを確認する。これらを満たした後に連続スコアで候補を比較する。高得点でも要求の削除や権限の退化は相殺できない。

一项固定 10 份文档、四域共 40 个判断单元的实验中，原方案由 Gemini 分析并评分，替代方案先让 Sol 分析、再由 Gemini 评分。参考一致数从 33 增至 38，问题类型 F1 从 56.3% 增至 88.4%。这项实验没有执行修复，且参考评审也来自 Sol；两组评分 token 上限存在差异，不能把全部变化归到同一个因素。With 10 fixed documents and 40 domain-level judgment units, the original setup used Gemini for both analysis and scoring. Replacing analysis with Sol while retaining Gemini scoring increased reference agreement from 33 to 38 and issue-type F1 from 56.3% to 88.4%. No repair was performed, the reference also came from Sol, and the scoring token caps differed, so this comparison changes more than one factor.10文書、四領域で計40判断単位を固定した実験では、元の構成はGeminiが分析と採点を担当した。分析をSol、採点をGeminiとすると、参照との一致は33から38、問題タイプF1は56.3%から88.4%へ上がった。ただし修復は実行せず、参照もSol由来で、採点トークン上限も異なる。変化を一つの要因だけに帰属させる比較ではない。

另一组 10 条完整修复对照却得到相反结果：生产 Judge–Fix 的独立参考通过数为 4 条，Verifier 只有 1 条。原始 145 个问题分别关闭了 133 个和 15 个。A separate end-to-end repair comparison on 10 cases went the other way. Production Judge–Fix passed four cases against the independent reference; Verifier passed one. They closed 133 and 15 of the original 145 issues, respectively.別の10件の全修復比較では逆の結果だった。独立参照での合格は本番Judge–Fixが4件、Verifierが1件。元の145問題のうち、それぞれ133件と15件を解消した。

Verifier 的 153 次 Fix 中有 66 次重复候选、53 次补丁无法应用，32 个候选进入后续接纳比较。最终 6 条仍保留初始文档，第 4 轮之后一直增加到第 24 轮，也没有增加内部准出。新增问题虽少，原问题却大多还在。Among Verifier’s 153 Fix attempts, 66 were duplicate candidates and 53 had inapplicable patches; 32 reached the subsequent acceptance comparison. Six cases ultimately retained their initial documents. Extending from round 4 through round 24 added no internal acceptances. Few new issues appeared, but most original issues remained.Verifierの153回のFixには重複候補66件、適用不能なパッチ53件があり、後続の採用比較まで進んだ候補は32件だった。最終的に6件は初期文書のままで、第4回以降、第24回まで増やしても内部准出は増えなかった。新規問題は少ないが、元の問題の多くが残っていた。

结构化修复目标的单次对照也暴露了相似问题。N02 把净现金流改成收入，N04 用创建人替代业务负责人：报错可能消失了，需求却变了。这组 10 个修复事务的 token 减少约 25.6%，可安全接纳的候选从 6 个降到 5 个。下一步必须确认目标真的实现，而不是只检查旧问题是否还出现在新列表中。A single comparison of structured repair targets exposed the same risk. N02 replaced net cash flow with revenue; N04 replaced the business owner with the record creator. The error disappeared by changing the requirement. Across 10 repair transactions, tokens fell about 25.6%, while safely acceptable candidates fell from six to five. Acceptance must verify that the target was achieved, not merely that an old error vanished from a new list.構造化した修復目標の単回比較でも同じ危険が現れた。N02は純キャッシュフローを収入へ、N04は業務担当者を作成者へ置き換えた。エラーは消えても要求が変わっている。10修復トランザクションでトークンは約25.6%減ったが、安全に採用できる候補は6件から5件になった。新しい一覧から旧エラーが消えただけでなく、目標が実現したかを確認する必要がある。

格式通过以后，还要看业务Check semantics after formatting形式の確認後も業務要件を検証する

格式模块处理下游无法可靠读取的表达问题。若修复需要改变字段来源、授权范围或业务资源，就应交回业务域，而不能当成标点或结构整理。The formatting module handles expressions that downstream consumers cannot reliably read. Changes to field sources, authorization scope, or business resources belong back in a domain repair, not in punctuation or structural cleanup.形式モジュールは下流が安定して読めない表現を処理する。フィールドの出所、認可範囲、業務リソースを変える修復は、句読点や構造整理としてではなく、業務領域へ戻して扱う。

1,312 条历史未准出样本继续修复后，831 条准出，与此前 3,168 条合并形成 3,999 条交付数据。这是多轮累计结果，不是同一配置从原始输入出发的一次通过率。剩余 481 条中，补丁无法写入和严格格式未过各占 108 条；其他还包括语义预算、复核协议、语义不等价等原因。Continuing repair on 1,312 previously unreleased samples accepted 831, which joined 3,168 earlier samples for a delivery of 3,999. 交付后扫描也需要核对规则。94 条“工作流非标准 Key”里，88 条是当前规则允许的通知正文 Key；另外 6 条确有非标准 Key，旧准出 2 条，恢复后准出 4 条。不能把规则差异全部算成漏判，也不能因为多数是误报而忽略真实错误。Post-delivery scans also need rule checks. Verifier 则先修两类判断：不能仅凭对象名称相互包含就把新旧问题合并；不能仅凭修后列表不再报错就认为目标关闭。H003 检验旧问题是否误判为新增，N02/N04 检验指标和负责人是否被偷偷替换。现有函数已发现这些判定风险，但尚未复现证明它们就是每个历史案例的直接原因。Verifier should correct two judgment patterns: merging old and new issues merely because object names overlap, and declaring a target closed because it disappears from the post-repair list.
