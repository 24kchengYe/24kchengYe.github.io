从设计到产物：训练规则评审模型From designs to artifacts: training rubric judges設計から成果物へ：ルール評価モデルの訓練

一份设计通过评审，落地的系统仍可能遗漏字段、接错工作流或放宽访问范围。我们把评审放在两个位置：先检查 Query + Spec，用 Judge–Fix 修好设计；再让 Code Agent 按 Spec 搭建产物，将实际产物解析成 Markdown，重新对照原始 Query 验收。A design can pass review while the built system still omits a field, wires a workflow incorrectly, or grants too much access. We review at two points: first Query + Spec, using Judge–Fix to repair the design; then Code Agent builds from the Spec, the actual artifact is parsed into Markdown, and the result is checked against the original Query.設計が審査を通過しても、実装ではフィールドの欠落、ワークフローの誤接続、アクセス範囲の過大設定が起こり得る。評価点を2つ置く。まず Query + Spec を Judge–Fix で審査・修正する。次に Code Agent が Spec から構築し、実際の成果物を Markdown に変換して、元の Query に照らして検収する。

Judge Infra Model 包含这两类专用评审模型：Spec-RJM 学习设计评审，Artifact-RJM 学习产物评审。它们共享规则分层与结构化裁决的思路，但输入、规则和训练标签分别构建。产物侧还保留既有 E2E Judge，作为独立流程对照。Judge Infra Model covers two specialist judges: Spec-RJM for designs and Artifact-RJM for built artifacts. They share hierarchical rubrics and structured judgments, while inputs, rules, and training labels are constructed separately. The existing E2E Judge remains a separate comparison pipeline on the artifact side.Judge Infra Model は、設計を評価する Spec-RJM と、実際の成果物を評価する Artifact-RJM を含む。ルールの階層化と構造化判定という考え方を共有し、入力・ルール・学習ラベルはそれぞれ構築する。成果物側では、既存の E2E Judge も独立した比較パイプラインとして残す。

2026年7—10月，Spec-RJM 从历史数据和业务规则开始，依次尝试监督微调（SFT）、强化学习（RL）、概率蒸馏（OPD）及理由监督（CoT）。后期比较使用按原始需求隔离的7,127条训练样本、792条测试样本。实验逐渐明确了几个选择：完整规则仍有必要；多问题RL在四组实验中有三组提高了错误类型F1；加入教师显式理由的三组对照中，仅学习裁决的方案表现更好。From July to October 2026, Spec-RJM progressed from historical data and business rules through supervised fine-tuning (SFT), reinforcement learning (RL), on-policy distillation (OPD), and rationale supervision (CoT). Later comparisons used 7,127 training units and 792 test units grouped by original request. Full rules remained useful; multi-issue RL improved error-mode F1 in three of four experiments; and verdict-only training outperformed explicit teacher rationales in the three-arm comparison.2026年7〜10月、Spec-RJM では過去データと業務ルールを整備し、教師あり微調整（SFT）、強化学習（RL）、確率蒸留（OPD）、理由の監督（CoT）を比較した。後半は元の要求ごとに分離した学習7,127単位・テスト792単位を使用。詳細なルールは有用で、複数問題の RL は4組中3組でエラーモード F1 を改善し、教師の明示的理由を比較した3条件では判定のみの学習が優れた。

这些结果还没有解决评审的全部问题。专用模型仍容易漏报，同类问题发生在多个对象上时尤其如此。实际产物评审则暴露出较多误报。研究后半段因此开始关注判断依据：怎样检查一个结论用了哪些事实，哪些前提尚未确认，以及前提改变后需要重审什么。Specialized models still miss issues, especially when the same error occurs on several objects. Reviews of built applications exposed more false positives. The later work therefore focuses on judgment grounds: which facts support a conclusion, which premises remain unconfirmed, and what needs reassessment when a premise changes.専用モデルには依然として見逃しがあり、特に同種の誤りが複数の対象で起こると弱い。構築済み成果物の審査では誤報も多く見つかった。後半は、結論が使った事実、未確認の前提、前提変更後の再審査対象という判断根拠に注目した。

1　模型要学会怎样评审1 · What a model must learn to review1　モデルが学ぶべき評価

两类评审都以用户需求为准。Spec Judge 检查方案是否说清楚、能否实现；产物 Judge 要找到已经创建的对象与实际配置，核对字段类型、引用、筛选范围及动作依赖。更高的验收要求体现在实现证据：设计中写了“提醒负责人”，不能替代工作流里的接收人配置；静态配置本身也不能证明消息已经送达。Both judges use the user request as the standard. The Spec Judge checks whether the design is explicit and feasible. The artifact Judge must find created objects and actual configuration, checking field types, references, filter scopes, and action dependencies. The stronger acceptance requirement is implementation evidence: writing “notify the owner” in a design cannot substitute for a configured recipient, and static configuration alone does not prove delivery.どちらもユーザーの要求を基準とする。Spec Judge は設計が明確で実現可能かを確認し、成果物 Judge は作成済みのオブジェクトと実設定を探し、フィールド型、参照、絞り込み範囲、アクションの依存関係を確認する。検収で追加されるのは実装の証拠だ。設計に「担当者へ通知」と書かれていても受信者設定の代わりにはならず、静的設定だけでは通知の到達も証明できない。

多维表格的设计包括表结构、视图、仪表盘、工作流和权限。例如，“订单逾期后提醒负责人”需要到期时间、逾期判断、提醒对象和触发流程配合。只写了“发送提醒”，并不能说明方案已经满足需求。Bitable designs include tables, views, dashboards, workflows, and permissions. A request to notify an owner when an order is overdue needs a due date, an overdue condition, a recipient, and a trigger to work together. Merely writing “send a notification” does not establish that the requirement is satisfied.多次元テーブルの設計には表構造、ビュー、ダッシュボード、ワークフロー、権限がある。「注文が期限超過したら担当者へ通知する」には期限、超過判定、通知先、トリガーの連携が必要で、「通知する」とだけ書いても要求を満たしたとはいえない。

我们把这些检查整理成逐条业务规则，称为rubric。每条规则写清适用条件、违规情形和例外。模型读入用户需求、一版待评设计、一个业务域的完整规则，输出是否通过、具体问题、错误类型、严重程度及判断依据。We organized these checks into explicit rules—a rubric. Each rule specifies applicability, violations, and exceptions. Given the requirements, one design version, and a domain's full rules, the model returns a verdict, specific issues, error types, severity, and supporting grounds.検査項目を逐条のルーブリックに整理し、適用条件、違反、例外を明記した。モデルは要求、評価する設計の一つの版、ある業務領域の完全なルールを読み、合否、具体的問題、エラータイプ、重大度、判断根拠を出力する。

一条评审样本是“一条需求 × 一版设计 × 一个业务域”。One review example is one requirement × one design version × one domain.一つの審査サンプルは「一つの要求 × 一つの設計版 × 一つの業務領域」である。 同一需求可能产生多个设计版本，也会拆成多个业务域样本。训练和测试按原始需求整组切分，避免同一需求的不同版本出现在两侧。 A requirement may produce several design versions and multiple domain examples. Training and test sets are split by original requirement so its versions cannot appear on both sides. 同じ要求から複数の設計版や領域別サンプルが生じる。訓練とテストは原始要求単位で分け、同じ要求の異なる版が両側に入らないようにする。

主要指标是错误类型F1，综合考察误报和漏报。计分按业务域、问题大类、规则及错误类型匹配标签，在每条样本内去重。同一种错误出现在三个对象上，报告其中一处就可能获得这个标签的全部分数。因此，我们同时检查问题数量、完整匹配和具体证据。The main metric is error-type F1, balancing false positives and misses. Labels match on domain, issue category, rule, and error type and are deduplicated within each example. If the same error appears on three objects, reporting one can earn full credit for that label. We therefore also inspect issue counts, exact matches, and specific evidence.主指標はエラータイプF1で、誤報と見逃しを合わせて測る。領域、問題大分類、ルール、エラータイプでラベルを照合し、サンプル内では重複排除する。同じ誤りが三つの対象にあっても、一つ報告すればそのラベルの満点を得る可能性があるため、件数、完全一致、具体的根拠も調べる。

后期792条测试使用Sol、DeepSeek生成的两套参考。这里的F1衡量参考一致性，语义争议仍需要复核；其中50条曾用于提示词开发。较早两组多问题RL及后三组OPD使用另一套1,056条共同测试和该批冻结参考，两套测试分别比较。F1按可评分输出计算，异常输出另计，严格一致按全部测试样本计算。The later 792-example test has two references, generated by Sol and DeepSeek. F1 measures agreement with those references; semantic disputes still need review, and 50 examples had been used for prompt development. Two earlier multi-issue RL runs and three later OPD runs use a separate common test of 1,056 examples with its frozen reference. We compare these test sets separately. F1 uses scorable outputs, exceptions are counted separately, and strict agreement uses all test examples.後半の792件テストにはSolとDeepSeekによる二つの参照がある。F1は参照との一致を測り、意味上の争点には再審査が必要で、うち50件はプロンプト開発で使用済みである。初期の多問題RL二群と後半のOPD三群は、別の共通1,056件テストと固定参照を使い、二つのテストは別々に比較する。F1は採点可能な出力を対象とし、異常出力は別計上、厳密一致は全テストを分母とする。

四种训练方法提供了不同的学习信号。SFT学习完整答案；RL对模型自己生成的答案计分；OPD让固定教师沿学生的生成过程提供词元概率；CoT比较不同形式的理由目标。提供指导的模型称为教师，接受训练的模型称为学生。The four methods provide different learning signals. SFT learns complete answers. RL scores answers generated by the model. OPD uses a fixed teacher to provide token probabilities along the student's generation. CoT compares different rationale targets. The guiding model is the teacher; the trained model is the student.四手法の学習信号は異なる。SFTは完全な回答を学び、RLは自分で生成した回答を採点する。OPDは固定教師が学生の生成過程に沿ってトークン確率を与え、CoTは理由ターゲットの形式を比較する。指導するモデルを教師、訓練されるモデルを学生と呼ぶ。

2　从数据和规则开始2 · Start with data and rules2　データとルールから始める

训练数据首先遇到的是版本错配。一条需求经过修复会留下多版设计，旧评审指出的问题可能已经在新版里消失。如果把新版设计配上旧标签，模型就会被教成“这里还有错”。因此，每份标签都要绑定它实际评过的设计版本和业务域；修复后的版本重新评审。The first data problem was version mismatch. Repair produces several designs for one request, and an issue in an old review may already be fixed in the new design. Pairing that design with the old label teaches the model to report a problem that is no longer there. Each label therefore has to stay attached to the exact design version and domain it reviewed; repaired versions are reviewed again.学習データで最初に直面したのは、バージョンの取り違えでした。一つの要求に対して修復後の設計が複数残り、古い評価の指摘は新版ですでに解決していることがあります。新版に旧ラベルを付けると、存在しない問題を報告するよう教えてしまいます。そのため、ラベルは実際に評価した設計バージョンと領域に結び付け、修復後の版は改めて評価します。

早期数据实验尝试增加正常设计、扩大独立需求覆盖、调整多问题输出及重采样。在共同200条测试上，扩大需求覆盖的一组细规则F1为63.67%，早期单层规则训练为53.82%。增加正常设计后，模型开始能够放行正常样本，但问题召回下降；四组的多问题全命中率都为0。训练规模和输出形式同时变化，这一阶段主要发现了数据需要补足的方向。Early data experiments added valid designs, expanded independent requirement coverage, changed multi-issue outputs, and resampled. On a common 200-example test, broader requirement coverage reached 63.67% fine-rule F1 versus 53.82% for early single-level-rule training. Adding valid designs helped the model pass valid examples but reduced issue recall; all four groups had zero all-issues recall on multi-issue cases. Training size and output format changed together, so this stage mainly identified data gaps.初期には正常設計の追加、独立要求の拡充、多問題出力の変更、再標本化を試した。共通200件テストで要求を広げた群の細粒度ルールF1は63.67%、初期の単層ルール訓練は53.82%だった。正常設計を加えると正常例を通せるようになったが問題再現率は下がり、四群とも多問題の全件検出率は0だった。規模と出力形式が同時に変わっており、この段階では主に不足データの方向を把握した。

规则本身也影响模型判断。我们一方面补充适用前提、例外和问题归属，另一方面要求先列出对象，再逐项扫描，发现一处问题后继续检查。Rules themselves shape judgments. We added applicability conditions, exceptions, and issue ownership, and asked the model to enumerate objects, scan each one, and continue after finding an issue.ルール自体も判断に影響する。適用前提、例外、問題の帰属を補い、対象を列挙して順に走査し、一つ見つけても確認を続けるよう求めた。

规则写清楚，判断和重复稳定性都能改善。不过，增加字段并不总有收益：在另一轮相同规则的比较中，要求额外填写对象、需求证据和设计证据，F1从90.32%变为89.43%。这些字段有助于人工复核，本次没有提高细标签得分。Clearer rules improved judgments and repeatability. 标签生产也经历了调整。多轮评审投票会保留共同遗漏，直接让复核模型改答案又可能删掉成立的问题。后来的流程先合并候选，再核对证据、前提和例外，最后补查遗漏；未解决的分歧单独保留。Label production also changed. Voting can preserve shared omissions, while letting a review model rewrite answers directly can delete valid issues. The later workflow merges candidates, checks evidence, premises and exceptions, then searches for omissions. Unresolved disagreements remain separate.ラベル生成も変えた。投票は共通の見逃しを残し、再審査モデルによる直接書き換えは成立する問題を消す場合がある。後の処理は候補を統合し、根拠、前提、例外を照合し、最後に漏れを探す。未解決の不一致は別に保持する。

补数据时，我们优先寻找训练里缺少的错误类型。历史问题用于定位候选，Sol 重新标注时只看需求、设计和当前完整规则，不看旧标签。经过补样和复审，错误类型覆盖从 190 种扩大到 249 种，得到 7,919 个领域评审样本。Data expansion focused on error types missing from training. Historical issues helped locate candidates, but Sol relabeled them from the request, design, and current full rules without seeing old labels. Additional sampling and review expanded coverage from 190 to 249 error types, yielding 7,919 domain-review samples.データ追加では、学習に不足している誤りの種類を優先しました。過去の指摘は候補探しに使いますが、Solの再ラベル付けには旧ラベルを渡さず、要求・設計・現行の完全な規則だけを入力しました。追加収集と再評価により、誤りの種類は190から249に増え、7,919件の領域評価サンプルを得ました。

按原始需求整组切分，7,127 条用于训练，792 条用于测试；同一需求的不同设计不会跨到两侧。训练同时保留正常、单问题和多问题设计，让模型既学会找错，也学会放行。测试覆盖 249 种训练错误中的 116 种，因此后面的总体 F1 还不能回答其余类型学得怎样。Splitting by original request gives 7,127 training samples and 792 test samples, keeping different designs for the same request on one side. Training includes clean, single-issue, and multi-issue designs so the model learns both to flag problems and to accept valid work. The test covers 116 of the 249 error types in training; its overall F1 does not establish performance on the remaining types.元の要求単位で分割し、学習7,127件、テスト792件としました。同じ要求の別設計が両側に分かれることはありません。正常・単一問題・複数問題の設計を残し、指摘すべき場合と通過させる場合の両方を学習します。テストが含むのは学習側249種のうち116種であり、後述の総合F1だけでは残る種類の習得度は分かりません。

3　SFT建立了基线，主要短板是漏报3 · SFT establishes a baseline, but misses issues3　SFTの基準と見逃し

SFT的训练输入包含完整规则、需求和设计，目标是完整JSON评审答案：每类检查给出状态，每条问题包含规则、错误类型、严重程度及一句话依据。后面的CoT实验是在这个基础上额外加入整段判断理由。SFT inputs contain full rules, requirements, and a design.
