从设计到产物：训练规则评审模型

一份设计通过评审，落地的系统仍可能遗漏字段、接错工作流或放宽访问范围。我们把评审放在两个位置：先检查 Query + Spec，用 Judge–Fix 修好设计；再让 Code Agent 按 Spec 搭建产物，将实际产物解析成 Markdown，重新对照原始 Query 验收。

Judge Infra Model 包含这两类专用评审模型：Spec-RJM 学习设计评审，Artifact-RJM 学习产物评审。它们共享规则分层与结构化裁决的思路，但输入、规则和训练标签分别构建。产物侧还保留既有 E2E Judge，作为独立流程对照。

2026年7—10月，Spec-RJM 从历史数据和业务规则开始，依次尝试监督微调（SFT）、强化学习（RL）、概率蒸馏（OPD）及理由监督（CoT）。后期比较使用按原始需求隔离的7,127条训练样本、792条测试样本。实验逐渐明确了几个选择：完整规则仍有必要；多问题RL在四组实验中有三组提高了错误类型F1；加入教师显式理由的三组对照中，仅学习裁决的方案表现更好。

这些结果还没有解决评审的全部问题。专用模型仍容易漏报，同类问题发生在多个对象上时尤其如此。实际产物评审则暴露出较多误报。研究后半段因此开始关注判断依据：怎样检查一个结论用了哪些事实，哪些前提尚未确认，以及前提改变后需要重审什么。

1　模型要学会怎样评审

两类评审都以用户需求为准。Spec Judge 检查方案是否说清楚、能否实现；产物 Judge 要找到已经创建的对象与实际配置，核对字段类型、引用、筛选范围及动作依赖。更高的验收要求体现在实现证据：设计中写了“提醒负责人”，不能替代工作流里的接收人配置；静态配置本身也不能证明消息已经送达。

多维表格的设计包括表结构、视图、仪表盘、工作流和权限。例如，“订单逾期后提醒负责人”需要到期时间、逾期判断、提醒对象和触发流程配合。只写了“发送提醒”，并不能说明方案已经满足需求。

我们把这些检查整理成逐条业务规则，称为rubric。每条规则写清适用条件、违规情形和例外。模型读入用户需求、一版待评设计、一个业务域的完整规则，输出是否通过、具体问题、错误类型、严重程度及判断依据。

一条评审样本是“一条需求 × 一版设计 × 一个业务域”。 同一需求可能产生多个设计版本，也会拆成多个业务域样本。训练和测试按原始需求整组切分，避免同一需求的不同版本出现在两侧。

主要指标是错误类型F1，综合考察误报和漏报。计分按业务域、问题大类、规则及错误类型匹配标签，在每条样本内去重。同一种错误出现在三个对象上，报告其中一处就可能获得这个标签的全部分数。因此，我们同时检查问题数量、完整匹配和具体证据。

后期792条测试使用Sol、DeepSeek生成的两套参考。这里的F1衡量参考一致性，语义争议仍需要复核；其中50条曾用于提示词开发。较早两组多问题RL及后三组OPD使用另一套1,056条共同测试和该批冻结参考，两套测试分别比较。F1按可评分输出计算，异常输出另计，严格一致按全部测试样本计算。

四种训练方法提供了不同的学习信号。SFT学习完整答案；RL对模型自己生成的答案计分；OPD让固定教师沿学生的生成过程提供词元概率；CoT比较不同形式的理由目标。提供指导的模型称为教师，接受训练的模型称为学生。

2　从数据和规则开始

训练数据首先遇到的是版本错配。一条需求经过修复会留下多版设计，旧评审指出的问题可能已经在新版里消失。如果把新版设计配上旧标签，模型就会被教成“这里还有错”。因此，每份标签都要绑定它实际评过的设计版本和业务域；修复后的版本重新评审。

早期数据实验尝试增加正常设计、扩大独立需求覆盖、调整多问题输出及重采样。在共同200条测试上，扩大需求覆盖的一组细规则F1为63.67%，早期单层规则训练为53.82%。增加正常设计后，模型开始能够放行正常样本，但问题召回下降；四组的多问题全命中率都为0。训练规模和输出形式同时变化，这一阶段主要发现了数据需要补足的方向。

规则本身也影响模型判断。我们一方面补充适用前提、例外和问题归属，另一方面要求先列出对象，再逐项扫描，发现一处问题后继续检查。

规则写清楚，判断和重复稳定性都能改善。不过，增加字段并不总有收益：在另一轮相同规则的比较中，要求额外填写对象、需求证据和设计证据，F1从90.32%变为89.43%。这些字段有助于人工复核，本次没有提高细标签得分。

标签生产也经历了调整。多轮评审投票会保留共同遗漏，直接让复核模型改答案又可能删掉成立的问题。后来的流程先合并候选，再核对证据、前提和例外，最后补查遗漏；未解决的分歧单独保留。

补数据时，我们优先寻找训练里缺少的错误类型。历史问题用于定位候选，Sol 重新标注时只看需求、设计和当前完整规则，不看旧标签。经过补样和复审，错误类型覆盖从 190 种扩大到 249 种，得到 7,919 个领域评审样本。

按原始需求整组切分，7,127 条用于训练，792 条用于测试；同一需求的不同设计不会跨到两侧。训练同时保留正常、单问题和多问题设计，让模型既学会找错，也学会放行。测试覆盖 249 种训练错误中的 116 种，因此后面的总体 F1 还不能回答其余类型学得怎样。

3　SFT建立了基线，主要短板是漏报

SFT的训练输入包含完整规则、需求和设计，目标是完整JSON评审答案：每类检查给出状态，每条问题包含规则、错误类型、严重程度及一句话依据。后面的CoT实验是在这个基础上额外加入整段判断理由。

最后一轮比较三个起点：Seed2 Lite基础模型；先做中间训练、再学旧版评审的模型；做过中间训练、直接学本轮评审的模型。中间训练指本次评审微调之前的额外训练经历。三组最终都使用同一批7,127条Sol标签及完整规则。

三组保持相同的 LoRA 训练设置，只比较模型起点：冻结主体参数，在同一批数据上训练两轮。训练文件内部另划验证集，外部 792 条用于最终评测；详细超参数见技术报告。

直接使用通用模型仍更强。在同一792条输入和完整规则下，Sol High、Luna Medium、DeepSeek V4.1 Flash、DeepSeek V4 Pro按Sol参考的F1分别为68.28%、65.01%、60.61%、65.12%，均高于本次专用训练模型；可评分输出分别为792、784、756、792条，Luna有8条异常，Flash有36条截断。DeepSeek参考下Pro的72.42%较高，说明模型排序也受参考来源影响。

4　RL怎样奖励模型找全问题

RL从SFT模型继续训练，让模型先生成答案，再按答案质量更新参数。首轮奖励根据去重后的大类、规则和错误类型计分，分别尝试混合正常设计、只用问题样本。两组训练到200步，在共同500条测试上，F1从SFT起点的46.20%降至42.65%、38.25%。混合数据使参考无问题样本仍判无问题的比例从64.34%升至78.29%，却漏掉更多问题；只用问题数据时，这一比例降到0.78%。

后续同时调整数据和奖励。训练按无问题、1个问题、2—3个问题、4个以上问题组织；正常样本尽量取同一需求修复后的设计，多问题答案完整保留。较早规则使用810条训练、242条验证，外部测试1,056条；统一规则使用795条训练、215条验证，外部测试792条。每批数据各从两个SFT起点继续训练，共四组。

四组采用GRPO：每步选32条输入，每条生成8份答案，以同一输入下的相对得分更新模型。共同运行80步，学习率0.000001，KL约束系数0.001，每10步验证；生成温度0.7，答案上限10,000 token。参考标签仅在奖励侧，学生作答时看不到。

奖励的关键变化是保留错误出现次数。三个对象犯同一种错，报告一处和三处应得到不同奖励。答案先通过JSON、标签、严重度和状态校验，再计算三层计数F1：

综合得分 = 0.2 × 大类F1 + 0.3 × 规则F1 + 0.4 × 错误类型F1 + 0.1 × 完全匹配
最终奖励 = 2 × 综合得分 − 1

计数F1为“2 × 命中条数 ÷（预测条数＋参考条数）”。完全匹配要求错误类型及数量全部相同。双方都无问题时奖励为1；只有一方有问题，或格式校验失败时为−1。

奖励保留数量，外部F1仍按去重标签计算。奖励还只检查理由非空、没有字面重复，尚未检查依据是否成立、是否指向正确对象。这使得标签、数量、对象正确性成为三个需要分别验证的问题。

四组多问题训练有三组提高F1。较早规则的两组分别提高约3.45、2.77个百分点；统一数据上，一组从56.97%到58.91%，另一组从56.19%到55.81%。正常设计、多问题数据及计数奖励共同构成了更有希望的方案，但这些因素一起变化，各自贡献还未分离。

训练停止位置也值得复查。直接学习新版规则的一组，第50步验证奖励为0.4629，最终第80步降至0.4184；目前外部测试使用第80步。中间模型是否更好，还需要在同一外部测试上验证。

5　OPD能否让学生少读一些规则

完整规则很长。OPD（On-policy Distillation）尝试让教师保留详细规则，学生只读精简版本：保留规则大纲、合法标签及输出格式，删除适用前提、排除条件和证据要求。

当前学生先生成答案，固定教师沿学生已经写出的前缀计算后续词元概率，学生据此调整概率分配，再生成下一批。每个输入生成1份答案，每批32条；取学生概率最高的64个候选词元，在其中重新归一化，用反向KL衡量概率差异，按词元平均计算。最终裁决的额外奖励关闭，教师获得的标签提示不进入学生输入。

首轮固定7,127条输入、Seed2 Lite基础学生和精简规则，训练223步。三个基础模型教师分别得到数量及扫描方向、参考理由、逐条标签，按Sol参考，792条测试F1分别为20.98%、20.69%、22.01%；专用SFT教师的一组为16.09%，其中657条输出为空问题集合。这轮没有达到压缩规则的目标。

下一轮固定同一个RL教师、6,580条训练输入及Seed2 Lite基础学生，训练206步，在共同1,056条测试上比较教师标签提示和学生规则长度。

三个已运行条件的F1分别为：教师不额外看标签、学生用完整规则，52.85%；教师看标签、学生用完整规则，51.12%；教师看标签、学生用精简规则，35.03%。教师不看标签、学生用精简规则的第四格未运行。

教师都有标签时，完整学生规则高16.09个百分点；学生都用完整规则时，增加教师标签没有提高结果。三组仍低于同集SFT的59.49%和RL的62.25%。学生提示在训练及评测时同步改变，当前能确认的是完整规则方案更好。若要继续缩短输入，需要逐类删减规则，检查哪些适用条件和例外必须保留。

6　学习教师理由，是否更容易判断正确

CoT实验用DeepSeek生成的同一批标签构造三种目标：理由放在普通回答里；同一段理由放在专用推理字段；只保留裁决。理由来自教师按要求输出的judge_reason，去掉置信度字段，与接口返回的原生推理文本有区别。

三组共用7,127条输入、同一裁决和完整规则，从同一Seed2 Lite基础模型做两轮LoRA训练。训练长度上限32,768 token；评测上限16,384，temperature为0.01，评测输入没有教师理由。

仅裁决方案在两套参考下都更好。Sol参考下，回答内理由、推理字段理由、仅裁决三组F1为41.54%、42.94%、51.52%；DeepSeek参考下为47.04%、46.98%、56.56%。以原始需求为单位配对重复抽样，仅裁决相对两组理由方案的四个差值，95%区间均高于0。

这组结果支持保留“仅裁决”的训练基线，但还不能把下降归因于理由内容。加入理由也拉长了训练目标，推理字段组还开启了不同的推理模式。下一次对照需要分别控制目标长度、训练步数和推理模式，才能知道模型究竟在哪一步受了影响。

我们也探索过更适合训练的理由。原生理由50条小试中，47条有合法裁决、3条截断；原文在两种格式下分别有12、11条超32k，整理后都能容纳，但仍有理由和裁决冲突、整理遗漏条件。固定10条修改提示词后修正了一条冲突，合法裁决却从9条变为8条，另有漏判未解决。

另一条路线让学生借助教师分析生成短理由，每条尝试4次，检查结构、标签及同类问题次数，取最早通过的一份。62条均未通过，由两组共同排除，最终形成7,065条“短理由＋裁决”和“仅裁决”配对数据。自动筛选未检查全部理由证据，后续SFT尚未提交。

7　从设计评审到判断依据

Artifact-RJM：检查已经建好的产物

Artifact-RJM 每次只评一个域。System Prompt 提供该域的产品能力、输入解释、规则卡和输出协议；User Message 只含 domain、原始 query、当前域 artifact_markdown。Spec 留在 Code Agent 的生成输入中，不作为产物评审的额外需求；这样不会把模型自行扩写的设计当成用户必须接受的要求。

五域分别是 Table、Dashboard、Workflow、Permission、View。Formula、Lookup、Link 归 Table，表视图与 Form 归 View。每条问题必须满足规则前提、违规条件及证据要求，同一最小失败事实只归到一条最具体的规则；不同对象上的独立问题仍逐条保留。模型一次输出 Category → Rubric → Mode、固定严重度、理由及该域 verdict。

训练样本按“一条 Query × 一个产物域”组织。969 个 Case 按原始 Query 分组：872 个用于训练，97 个用于内部测试，对应 4,360 / 485 个评审单元。Luna medium 用完整规则生成单轮参考标签，Seed2 Lite 在同样的规则与输入结构下做两轮 LoRA SFT。Case 的作用是切分和聚合，实际训练单位是领域评审单元。

484条输出可解析，错误类型精确率32.45%、召回率53.98%、F1为40.53%。参考判定90个业务域失败，学生判定155个。模型容易把“管理”“模板”等词解释成必须创建自动化、表单或视图，同时漏掉Lookup唯一性、AI节点输入和重复触发问题。

训练覆盖235种登记错误中的84种，多问题单元占4.98%；测试中2—3问题的完整一致为4/22，4个以上为1/11。补数应优先覆盖需求适用与排除条件、同一规则的多对象问题，以及对象间的执行依赖。固定快照支持配置层判断；真实送达、执行结果及修改过程需要相应运行证据。

一个真实测试例说明了这个边界：用户要求先建主表、再填子表，并录入一道完整试题。产物没有 Workflow；Luna 判该域 pass，学生却报 missing_automation。学生把一次性的搭建顺序误读成了持续自动化需求。这个例子提示我们补充“需要自动化 / 只需完成搭建”的配对样本，同时继续检查真正的触发、引用和写入缺陷。

Artifact-RJM 与既有 E2E Judge 在同一份产物上对照。前者输出五域细粒度规则标签，再以“任一域 fail”聚合 Case；后者执行自己的子域评审和 Mix 全局仲裁。相同输入对象不代表相同规则或相同裁决机制。这里的 97 个 Case 使用固定 Markdown 重放，比较的是评审结果，不是重新搭建产物后的成功率。

DSH记录评审过程，ATMS管理判断前提

多路评审可能依赖同一个错误前提。DSH（DeepSeek Harness）提供模型会话、路由及调用记录，我们在其上搭建数据管线：有分歧的先复核，之后所有结果都检查事实、产品能力和待确认假设，交人工确认；规则改变后，重新检查受影响案例。

首轮试运行只跑通了部分双路评审，分歧复核和规则分析尚未产出有效结果。因此，当前可以展示的是标签管线的实现；要检验它能否减少错标或人工工作量，还需要让同一批样本走完复核和人工确认。

同一条“方案有问题”的判断，可能依赖不同依据。某项依据撤回后，判断是否还成立？我们提出用基于假设的真值维护系统（Assumption-Based Truth Maintenance System，ATMS）记录这些依赖。

输入用户需求、待评方案，以及已确认的产品能力和规则。AI提取明确需求及方案事实，把有依据的内容同待确认假设分开，记录推导关系。系统校验引用和依赖结构，再计算每条结论所需的最小假设组合，按已登记的冲突规则排除矛盾组合。人工复核时，可以同时看到判断、依据、待审假设及冲突状态。

下面用一个示例说明。已核验的事实F是“方案未限制客户数据访问”；待确认的A是“客户归属规则在本案例生效”，B是“客户保密条款在本案例生效”。两项规则都要求这一访问限制，因此登记两条推导：F ∧ A ⇒ V、F ∧ B ⇒ V。V表示“方案缺少应有的访问限制”。

V的支持集合是{{A}, {B}}：接受A或B中的任意一个，都有一条成立的推导路径；共同事实F不再列入假设集合。{{A,B}}则表示必须同时接受A、B，含义不同。

  • 撤回A，保留B：V仍由B这条路径支持。
  • A、B都撤回：V失去当前依据，需要重审；这不等于方案通过。
  • 新增豁免C：若C表示本案例豁免上述两项要求，且已明确登记{A,C}、{B,C}不可同时成立，那么接受B和C就产生前提冲突，需人工确认哪项适用。其他不含冲突的前提组合仍可保留。

ATMS据此回答“判断依赖什么、前提变化后什么需要重审”。前提是否真实仍需证据核验；支持路径的数量也不代表概率置信度。项目已实现引用哈希、缺失前提和循环依赖检查，支持集合传播、冲突组合管理及撤回查询尚待实现。

用配对数据检查决定性条件

因果配对合成要检查一件具体的事：只改变一条规则的适用条件，模型能否改变相关判断，同时保留其他判断？ 这样的样本可以帮助模型学习判断边界，例如区分“需求提到了负责人”和“本案例确实要求访问限制”。

继续用客户数据访问的教学例子。用户要求建立客户跟进表，记录客户名称、负责人、联系电话。方案已经配置前两项，缺少联系电话，也未限制客户数据访问。这里明确设定：保密条款B不适用，且没有其他访问限制要求；负责人字段仍由用户需求直接要求，不取决于归属规则A。

两份样本的需求、方案、规则正文都相同，只改规则上下文中的一个值：A从“适用”改成“明确不适用”。先登记三项预期，再让模型分别评审。

  • 应变化：访问限制缺失，从“应报”变为“本项不报”。这来自A明确不适用、B及其他相关要求已经排查，而非简单撤回一个待审假设。
  • 应保持：联系电话仍然缺失，两份样本都应报告；负责人字段已经配置，两份样本都不应报告缺失。因此，第二份方案仍有问题。

ATMS提供这一步的依据：访问限制结论V依赖F ∧ A，字段判断则不依赖A。先检查V是否还有其他支持路径，再登记哪些项应变、哪些应保持；预期答案留给复核人员，不放进待测模型的输入。若B仍适用，V就不应变化，这对样本也不能强行标成相反标签。

复核通过后，每对材料保存两份输入、唯一改动、逐项标签及支持依据。同一原始案例的所有变体放在同一个训练或测试分组，避免泄漏。验证分两步：先重复评审，检查应变项是否正确变化、不变项是否被误改；再固定模型起点、训练预算，比较加入配对数据能否减少误报、漏报。当前这是合成及验证方案，尚无配对训练收益。

8　接下来优先解决什么

这组实验建立了可追溯的数据、完整规则下的专用模型基线，以及几条有直接对照支持的选择：继续保留详细规则；兼顾正常设计及多问题样本；理由研究保留仅裁决基线。专用模型的质量差距、不同训练起点的收益差异，都还存在。

下一步优先检查对象和证据是否正确。模型可能报对标签、数对条数，却把理由指向错误对象。先建立这类错误的独立复核样本，才能判断应当补数据、改奖励，还是调整理由训练。

数据管线则需要先走完一小批完整流程：确认前提，形成支持集合，撤回假设并检查受影响结论，再验证配对数据能否改善学生判断。框架已经指出了需要记录什么，效果还需要实验回答。
