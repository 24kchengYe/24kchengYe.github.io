Judge–Fix 技术报告

2026 年 6—10 月

摘要

本研究面向多维表格设计文档的自动修复：模型根据用户需求和产品规则发现问题，修改 SpecDoc 或 HostPlan，并检查最终设计能否支持实际建表。2026 年 6—10 月，项目比较了局部修复、模型切换、历史反馈、投票、格式恢复和 Verifier 前后版本验证，形成了四域 Judge–Fix–Router 主链路及独立的修改验证路线。

实验表明，限制修改范围和澄清具体业务规则能改善部分固定样本上的修复结果：Non-Table 300 条中，保护合格段落使 Fix 阶段通过数从 156 增至 177；8 条工作流难例中，保留补丁方式、只补业务规则使准出数从 3 增至 7。更复杂的审核和更大预算没有稳定带来收益。Verifier 的前置分析在 40 个域判断单元中将参考一致数从 33 提高到 38，但另一组完整修复实验的参考通过数从 4/10 降至 1/10。下一步应先查明 Judge 报出的问题是否真实存在，再检查 Fix 是否修好问题并保留原需求，最后用端到端评测验证建表结果。

1. 引言

执行器按照多维表格设计文档实现用户需求。它既要说明有哪些表、字段、视图和流程，也要满足字段类型、组件能力和权限规则。设计中只写出一个目标名称，并不等于给出了可执行的方法。例如“培训完成度”可以是手工填报值，也可以是需要按培训记录自动汇总的结果；是否缺少计算方式，要结合用户需求和完整设计判断。

自动修复的困难有两部分。首先，Judge 必须区分业务缺口、能力限制和允许的表达差异，不能把正常设计误判成错误。其次，Fix 不仅要消除已报问题，还要保留原来的业务含义。将管理员改成只读，可能让一条权限限制通过，却使其无法完成管理职责；把净现金流改成收入，可能消除公式问题，却改变了指标。

主链路采用“按域检查—按依赖修复—修后重判”的方式处理这些问题。Verifier 则进一步比较修前与修后两份文档，显式判断目标是否关闭、原有需求是否保留。两者的研究目标相同，但检查得更细不代表最终修得更好，必须分别测量。

主要实验问题如下。

研究问题 被比较的方法 主要评价

2. 实验设置

输入是用户需求（Query）和待修设计。设计有两种格式：Markdown 形式的 SpecDoc，以及包含 goal/tasks 的 HostPlan JSON。四个业务域分别是数据表、仪表盘、工作流和权限。Table Fix 可以修表、字段和计算依赖；Non-Table Fix 修改后三域，遇到缺失的表或字段时交回 Table。

研究使用三类结果：链路准出是最终文档通过本次 Judge 和格式检查；独立参考复核是另一套模型评审对最终文档或修改前后对的判断；E2E是执行器建出 Base 后的业务评测。文中相关参考标签来自模型，未当作人工金标。

2.1 指标定义

样本级指标以完整 Query＋文档为单位；域级指标以“样本×业务域”为单位；问题级指标还区分规则类型与具体对象。Fix 阶段通过数、最终准出数和 E2E 通过数处于不同阶段，不能相互替换。调用数统计请求，token 统计模型处理的文本量；更高并发只改变同时运行的请求数。

成本对照报告总量，也检查每份参考合格文档的消耗。未实际推理的限流请求不计作业务失败。历史实验多数为单次或小规模定向对照；若样本被用于提示词开发，结果用于回归诊断，不写成未见样本上的泛化收益。

3. Judge–Fix 主链路

3.1 调度流程

主链路先检查四域，再根据依赖选择修复节点。表和字段是其他域的前置条件，因此缺少资源时优先修 Table；表结构稳定后，再修仪表盘、工作流和权限。每次修改后重新检查，普通阶段仍未解决的样本进入预算有限的难例阶段。

准出检查针对同一份最终文档。最多检查 V 次，至少 Q 次通过；已能确定多数结果时提前结束。格式模块随后检查文档能否按下游约定读取。格式修改若改变了文档，需要重新确认业务判断。最终导出保存实际文档、投票和失败原因。

3.2 Fix 内部流程

Fix 接收 Query、当前文档及待修问题，生成局部补丁或完整 JSON。程序先解析输出，再核对补丁是否真正应用。零匹配、多匹配、截断等错误进入输出恢复；候选写入成功后，才检查目标是否修复、是否允许替换当前版本。被拒绝时保留旧文档和失败原因，后续候选读取这些反馈。

一次进入 Fix 可以包含多轮，每轮也可以有多个候选。候选分别评估，不把不同候选的修改直接拼在一起。局部 Fix 通过后返回主链路，继续做整体检查。

3.3 文档格式适配

早期 HostPlan 适配分别修改了四域 Judge、两种 Fix、消息模板和文件映射。日期精度、公式输出类型、闭合选项、按月统计来源、跨任务依赖等被整理成业务规则，而不是持续追加具体坏例。

统一 Design 0-1 Judge 后，曾出现 Markdown SpecDoc 被 Fix 改成 {goal,tasks} JSON 的问题。后续通过显式文档格式和独立输出验证处理；Rewrite 作为单独任务，仅在需要转换格式时调用。业务检查通用，不意味着输入输出格式也必须相同。

4. Fix 策略实验

4.1 限制修改范围

本组分别检验增加能力说明、限制修改范围的效果。固定同一批 Non-Table 输入，比较原版、增加能力说明、再增加合格内容保护三种提示词；指标是 Fix 阶段通过数和已合格域的退化次数。

6 月首先比较旧版 Fix 与加入能力说明的新版。50 条小试曾显示旧版更好，扩到 300 条后，两版的 Non-Table Fix 阶段通过数分别为 156 和 154，差距很小。继续加入“保留合格段落，只修改问题及必要依赖”的约束后，通过数增至 177，记录中的域退化次数从 76 降至 47。

Non-Table，固定 300 条 Fix 阶段通过
原版 156/300
增加能力说明 154/300
增加合格内容保护 177/300

另一组 Table 对照中，两版都是 179/300，没有复现这项提升。因此保留下来的是按问题限制修改范围，而不是要求所有已有内容一律不能改。

跨域依赖决定了局部修复的边界。例如仪表盘、工作流同时依赖一个缺失字段，只改下游描述无法解决。Router 先让 Table 补齐字段，再回到相关域，避免各域分别生成互不一致的替代方案。

4.2 50 条样本策略对照

这组检验两种替代思路：修不好时换更强模型，或扩大候选的修改范围并增加审核。输入固定为同一批 50 条，记录最终准出、请求总量和输入输出 token。六种条件同时包含模型、历史信息及输出形式的变化，只有相邻条件明确只改一项时，才能单独解释该项影响。

这批已知难例支持先修业务规则。对象定位仍可用于具体的补丁失败，但不能仅凭“定位更稳定”就推断整链质量更高。全文条件的运行参数未完整启用预期 Supervisor，因此 2/8 只用于诊断实际执行方案，不评价未真正运行的完整审核方案。

5. Judge 配置

5.1 同版本多数投票

研究问题是：一次“通过”能否代表最终文档已稳定满足规则？早期实验对同一最终版本重新调用相同 Judge，观察通过判定是否翻转；后续才引入同版本多数投票。这里的重判差异反映模型评审波动，不等同于文档在重判时被修改。

早期 954 条难例修复中，累计曾通过 914 条，最终一次重判却只有 625 条通过。之后的 6,457 条集合也出现链内通过 6,291、单次独立重判通过 5,315 的差异。这推动链路保存文档版本，并用重复判断区分一次通过和多次一致通过。

对原链路或独立重判至少一次失败的 1,218 条，复用已有失败反馈进入难例 Router；每次完整四域检查算一票，三票至少两票通过。技术异常恢复后，最终准出 1,212 条：864 条三票全过，348 条两票通过。样本 002329 虽投票通过，仍含重复 JSON 尾部；输出验证因此不能由投票替代。

投票后来覆盖各个准出出口。V 是最多票数，Q 是通过门槛；导出记录保留修复阶段、票数和质量标签。需要第三票时，一票可能包含四个业务域的独立调用，不能将“12 个 case 需要第三票”计作 12 次单域 Judge。

5.2 降低调用成本

同一 43 条上的成本实验使用 GPT-5.5 作外部复核。Luna 并发 22 的方案通过 29/43，GPT-5.2 基线为 30/43；DeepSeek V4 Flash 在自身链路中全过，外部复核只有 10/43。因此模型选择同时看外部复核和调用成本，不采用自身放行数作为质量结论。

后续 Mixed Judge 采用 Luna：普通检查和前两票 medium，只有需要第三票时切 high。这里的 mixed 指推理强度混用，与 E2E 的 Building Mix 评测模式不同。

成本改动 处理方式 实测结果
多数锁定后早停 已确定达到或无法达到通过门槛时，不再凑满票数 与有效首票复用合计，146 个节点回放的调用 2,442→2,190，结论相同
复用同版本有效首票 刚完成且对应同一文档的四域全过，计入准出确认 文档、规则和模型配置必须一致
提高并发 分开控制 case 并行数和进程总请求量 一组并发 8→22，耗时 122.3→74.6 分钟；重试 10→286

离线回放固定了已有票据，证明的是相同判断下可以少调用；在线模型重新采样后，还会受到限流、重试和返回速度影响。因此少调用没有按相同比例缩短总耗时。重复配对实验的三次全过数增量也出现 +3、0、−4，单次差一两条不足以判定配置更优。

6. Verifier

6.1 验证一次修改

主链路主要判断“这份文档是否有问题”。Verifier 增加“这次修改是否值得接受”的判断：需要在相同需求下比较两个版本，不能只看新版本的错误列表是否变短。它同时研究问题覆盖、连续评分和候选接纳，不只是把原 Judge 换一个名字。

2026-07-23 的研究方案提出：在覆盖旧文档前，明确这次修改解决了哪些问题，是否删除需求或破坏正确功能。具体分成三种检查：

检查 输入 输出及用途
State：当前状态 Query、当前文档、业务规则 找出问题、对象和证据，作为 Fix 的目标
Transition：修改比较 原问题、修前文档、修后候选 确认目标是否关闭、需求是否保留、是否产生新问题；决定接受、回退或待确认
Release：最终检查 Query、最终全文、业务规则 判断整份文档是否满足准出要求

V12 指南的四域共 79 条 Rubric、181 种错误模式。State/Release 按域调用，一域一次请求，四域并行；不是每条规则调用一次。输出逐条对应选中的规则，缺项或重复项属于无效输出。Transition 检查修复目标、需求保留、可执行性和跨域一致性。

连续评分用于比较满足硬约束的候选。需求被删除、目标未解决或权限退化时，不能用更高的平均分抵消。最小实现每轮只生成一个候选，同时保留旧版；候选被拒绝时，下一轮读取失败反馈。V12 指南常规最多三次候选生成，难例第二阶段默认关闭。

概率读取也经历过修改：多个评分位置会遗漏低概率档位，十级量表难以稳定取得完整分布，A—E 又与候选名称混淆。后续 Transition 使用 P—T 五级量表，两版各请求一个评分位置。接口不支持原生概率时，可用独立成对投票，但分别记录。

连续评分的计算和用途如下。原生概率模式先取齐五个合法评分 token 的 logprob，在这五档内归一化，再按冻结的档位权重计算期望分；比较的是候选与修前版本的分差。

pg(x) = exp(ℓg(x)) / ∑h exp(ℓh(x))
s(x) = ∑g pg(x) · vg，　Δs = s(候选) − s(修前)

其中 ℓ 是接口返回的 logprob，v 是由差到好映射到 0—1 的五档权重。任一合法档位缺失，都不能把它的概率补为零；自动模式保留失败回执，改用完整的成对投票。投票交替交换两版的展示顺序，候选支持率为“（候选胜票＋0.5×平票）/有效票数”。这两种量分别记录，均不是经校准的“判断正确概率”。

接纳先检查硬约束，再看分数：目标未关闭、发生关键业务退化或跨域引用损坏，直接回退；通过这些检查后，才比较目标改善和应保留项的变化；证据不足则暂缓。接受一处修改也不代表整篇准出，仍要由 Release 检查最终全文。这些是已有设计，后文实验检验其实际效果。

7. 格式准出

7.1 格式模块

设计即使在业务层被判通过，仍可能因为补丁无法写入、结构不合规或资源引用含糊而不能交付。格式路线检验的是：能否把表达问题从业务修复中分离，同时不让格式修改改变语义。

格式模块在业务修复后检查下游要求的表达形式。只涉及表达的错误在本模块处理；需要改变字段来源、授权范围或业务资源的，交回对应 Fix。局部补丁后检查全文，避免修好一处却破坏其他章节。

失败统计需要区分：补丁未写入、严格格式未过、候选改变业务含义、复核响应无法解析、格式后业务投票失败，以及业务回修仍未完成。它们发生在同一个阶段，但需要改的代码或提示词不同。

8. 提示词回归实验

8.1 A—E 定向回归

这一系列检验：把 E2E 坏例归纳成通用规则后，能否减少同类缺口，而不引入无依据的收缩或扩写？早期用相同 checkpoint 检查可修复性，后期用原始 Building 50 同时检查准出和实际 Base。两种起点分别保留，避免把重复修复的效果当作提示词净收益。

9 月提示词实验首先针对三类问题：应计算的结果被写成普通字段，角色必要权限被缩成只读，以及修复工作流时改变了原来的处理范围。

计算案例中，Building Case 2 的“资源完成度”“培训完成度”仅有普通进度字段，没有计算或汇总来源。Judge 没指出生成方式缺失，Fix 就没有补；后续版本加入公式/Lookup 后，还需检查分母范围。规则因此要求对计算、汇总或条件判断产生的结果，核对其合法生成方式，而不是只查同名字段是否存在。

首批比较使用 8 份相同 checkpoint，来自 6 条 Query；Case 2、49 各有两份历史文档。各组均从同一 checkpoint 开始。

8.2 F—J 提示词改动

排查完整请求时发现，部分入口传入 OriginalSpecDoc 后会追加“本次不是第一次 Judge，语气、风格、结构变化也算问题”，即使它实际是首轮。该运行时消息与域规则允许等价表达冲突。F/G 阶段明确以当前全文判断，历史仅用于核对真实功能损失。

G 重点限制几类误改：不能因 Query 没逐字段授权就把角色设为全只读；保留必要关联输入；新增与编辑分别核对；拆流程不得扩大或缩小处理集合；不得删除办理动作、只留通知。14 条原始输入回归准出 9 条。H 增加完整输入、Lookup 类型和事件时序约束后为 8/14，Case 41、43 出现权限退化，未选为全量配置。

G 扩到原始 Building 50，链内准出 31 条，CodeAgent E2E 通过也为 31 条，但两者交集只有 24 条。I 在 G 上吸收扫描和 E2E 问题，修正过 Judge 中的 Fix 语气、统一用 1/0 AVG 表示完成率等不当规则。I12 仍准出 31/50，却有五条新增、五条减少，调用 6,681→7,463。固定候选的前两票也频繁分歧，变化同时含有规则影响和模型波动。

J 随后回到 G，明确 Workflow 记录筛选的左右值都不能沿 Link 下钻；同时要求替代写法保留记录身份、字段类型和原比较含义。后续 K/L/M 继续检验这些限制是否真正改善设计。

8.4 E2E 失败归因

评测固定输入设计，分别检查代码是否编译、是否执行完成，以及实际 Base 是否满足 Building Mix 的业务要求。出现失败时，按需求、修前/修后文档、代码、Base、Judge 输入逐层核对。一个案例可以同时有设计和执行问题。

历史评测处理过高级权限 Base 分组错误、旧 Base 复用、空模板表残留、专属 case 提示词索引错位、执行日志截断和 Viewer 绑定错误。这些都可能改变分数，应保留在实验配置和原始证据中。

10 月又以 G 提示词从原始 50 条重跑，Judge–Fix 准出 28 条，CodeAct E2E 通过 24 条。CodeAgent 组 20 次请求均遇到 429，另 30 条未启动，没有可用于比较的业务分数。它不应被记成 CodeAgent 能力为 0%。

9. 结论

以下结论依据截至 2026-10-16 收录的实验和实现。后续修改建议尚未经过新实验验证。

9.1 主要结论

目前证据支持保留局部内容保护、Table 优先的依赖路由、同版本投票早停，以及格式修改后的业务核对。前两类主要解决修改范围和依赖，后两类控制评审波动和交付风险；它们不是一种机制的不同名称。

具体业务规则在定向难例中产生过清楚收益，但整组增加约束没有稳定提高 E2E。G/K 中既有设计阶段真实退化，也有共用规则缺陷、执行问题和评审检出差异，不能只凭总分下降定位提示词责任。Verifier 已改善部分检查指标，完整修复仍受问题对象、补丁应用和接纳判断限制，尚不具备整体替代主链路的证据。

9.2 现有实现

局部补丁、输出恢复、有界对象替换、候选去重和回退、投票早停、格式恢复及业务回交都有实现。权限规则已包含职责核对，Table Fix 已要求计算结果有生成方式。历史失败需验证这些机制是否在相应入口生效，不再新增同名步骤。

9.3 必须修正的问题

位置 已查到的问题 修改范围
Workflow Judge / Non-Table Fix 一处禁止记录筛选沿关联字段下钻，另一处笼统允许“条件/筛选”下钻 合并冲突表述，按节点和参数位置判断；记录筛选左右值均禁止下钻，合法的其他引用保持原规则
Verifier policy.py::_same_issue_semantics 空对象或名称相互包含，可能直接被视为同一问题 优先使用已有表、字段、角色等定位信息；无法唯一确认时标待确认，不依据包含关系直接合并
Verifier policy.py::_target_check 修后列表中不再报同一问题，就可能被认定目标关闭 读取现有 State/Transition 证据，核对原需求仍被满足；删除、改名、缺少覆盖证据时不能直接关闭

Workflow Judge 负责识别不支持的引用；Non-Table Fix 负责替换写法，且不能改变原需求。建议分别修改如下：

Judge 建议：

按字段引用所在的节点和参数位置判断能力。查找、修改记录的筛选条件左右值均不得沿关联字段下钻；其他位置的引用按相应能力规则判断。使用 Lookup 等替代时，核对来源、输出类型、单值或集合及比较语义。

Fix 建议：

替换不支持的筛选引用时，保持原比较含义和目标记录范围。明确替代字段的来源、类型、单值或集合；需要补表字段时，反馈具体资源缺口。不用近似字段或文字承诺代替实现。

Building 38 是检查等义替代的用例。Verifier H003、N02/N04 分别说明对象比较和目标关闭需要验证，但尚未复现证明上述函数是这些历史案例的直接原因。此处修正具体判定，不追加全量 Judge，也不先建立新的全局对象 ID 系统。

路线 先验证的案例和反例 再看整体结果

补丁及重复候选 T01 的删除、T05 的锚点失败；核对实际写入、重复哈希和下一轮反馈 只有当前版本仍出现同类失败，才修改具体恢复分支，不重新加入已有去重机制

稳定对象 ID、全文重写、更多投票、扩大修复预算和替换模型暂不列为默认改动。现有对照没有支持将它们组合启用。下一轮先验证上述明确缺口，再决定是否扩大到完整数据集。
