Data Generation & Agentic RL for Seed Models

为 Coding Agent 构建训练轨迹

一个能用的产物，未必对应一条适合训练的轨迹。围绕多维表格搭建任务，我们把模型决策、工具调用和真实返回一起记录，比较 Spec 规划、在线纠偏与离线编辑，寻找质量与生成成本之间的取舍。

2026 年 10 月 · 实验笔记

任务从用户需求开始，涉及表、视图、仪表盘、工作流和权限。Seed 在 Harness 中读取技能、编写参数或脚本、调用 CLI；工具返回进入下一轮上下文。训练数据需要保留这条决策与执行的因果链。

Harness 如何承载一条轨迹

Online 生成与修复共用执行底座

Online 包含首次生成、运行时纠偏和评审后的有界重生成；教师监督覆盖每一次执行。这些执行共用同一个 Harness：上下文组装、工具环境、真实回执和检查点。Spec→TodoList 位于规划层，计划指导执行，问题归因更新计划。Offline 接收无需继续重生成的完整轨迹，沿依赖做编辑与核验；发现当前问题需要真实执行时，携问题与证据回流 Online。

例如，一条工作流依赖尚未创建的字段：TodoList 应先安排字段创建，再安排工作流；Harness 执行后把真实字段 ID 和返回写入轨迹；Online 在错误决策前恢复可继续执行的上下文与环境，再生成受影响后缀。若只需删除一次无副作用的失败调用并调整后文，Offline 可在核验依赖后局部编辑。涉及状态或返回值变化时，必须有对应的真实执行证据。

一次 Rollout 的执行循环

模型负责选择动作；Harness 负责组装上下文、分派工具调用、回填真实观察，并管理预算、检查点与执行账本。工具环境保存 Skills、脚本和参数文件，Bash 中的 lark-cli 连接云端 Base。下一轮决策同时依赖消息历史和此前已经改变的环境状态。

初始输入包含 ThinkSP、FunctionSP、MainSP、Reminder、原始 Query 和工具 Schema；Skills 正文通过 Read 按需进入上下文。模型能看到的是工具 observation，完整 ToolResponse 和运行元数据另作审计证据。后台任务的完成通知也会补回消息。续跑时，已完成调用按 call ID 和参数哈希复用真实回执；结果不明的写操作停止执行，交给新环境重试。

本批 Rollout 实际开放 5 个工具：Bash、Read、Write、Edit、present_files。本例调用了 Read、Bash、present_files，未调用 Write 或 Edit。更完整的线上工具定义还包含 Glob、Grep、TaskOutput、TaskStop、TodoWrite 等，但它们没有启用在这批轨迹的 tools[] 中。

抽象轨迹模型

抽象地看，每一轮都把历史消息与当前环境交给模型，由模型选择动作；Harness 执行工具并回填真实返回，形成下一轮状态。失败时保留回执与成本，在检查点恢复上下文和环境，再选择新的动作。

真实 Case：两次纠偏如何改变执行

选取在线纠偏实验中的一条库存搭建轨迹：模型读取技能，创建产品表与出入库记录表，写入样例，再创建表单、仪表盘并回读交付。实际产生 15 次模型响应，最终保留 13 轮。图中主线是保留轨迹，两次失败在对应检查点旁展开；回退后，模型重新选择动作并继续执行。

第一处纠偏在 T3：数字类型码触发 12 项参数校验错误；回到创建前，模型重写字段定义，采用 text、number、select 等字符串类型，重新执行后拿到创建成功回执。第二处在 T5：--records 不受支持，产品仍为 0 条；恢复 T1–T4 的上下文，并把已有 Base 复制为工作副本、映射资源 ID 后，模型先读 --help，再按 --json / create_records 写入，成功得到 6 个记录 ID。

两次失败尝试保留在审计日志和成本统计中，最终轨迹保留纠偏后的 13 轮。T10、T11 分别回读到 6 条产品和 6 条流水。T13 的“已完成”是模型回复，业务是否满足需求由 Judge 另行判断。这条记录展示了 Online 运行时纠偏的完整过程。

已做实验：Spec 如何参与规划

我们先在同一组 10 个需求上比较三种输入：只有 Query；把 Spec 放进 user 消息；把 Spec 作为非强制 reminder。三组都由 Seed 2.0 Lite 生成，最终产物统一按原始需求验收，评审输入不包含 Spec。

这组实验还暴露了两种质量的差别：部分产物通过验收，但轨迹在当时的过程评审中仍因严重问题得到 2 分。最终功能是否满足需求、执行过程是否适合模仿，需要分别测量。这里的历史轨迹评分不与后文的新评审协议合并。

Online：在错误发生处修复

执行中的代码或参数错误，由教师提供指导，回退到错误动作前重新选择。任务结束后，完整轨迹再接受三轮独立评审：同一问题至少两票才纳入归因。语义错误保留原 Query，从错误决策前恢复状态并重新生成后缀。

能力边界问题先检查是否存在保留全部明确要求的等价改写，通过后才从头生成，并继续按原始需求评审。网络、认证等环境故障单独记录。交接给 Offline 的是无需继续重生成的轨迹，以及原 Query、真实回执、评审和修复记录。

定向续跑，省下了什么

在 10 条问题定向抽样的轨迹中，我们分别从同一错误位置前恢复两个独立环境：一组无指导续跑，一组接收定向指导后续跑。代码与语义各 5 条，使用 GPT-5.6 Luna xhigh，每个条件独立评审三次。

代码 · 5 2.00 2.40 → 2.60 −27.3% −30.2%
语义 · 5 2.20 2.00 → 2.20 −20.8% −25.4%

分数为冻结的 1–5 分档聚合结果；成本变化比较定向与无指导后缀生成，不是整条教师与 Judge 链路成本。20 个新分支中 5 个预算失败，均保留在统计内；共完成 90 次有效评审。

定向指导减少了重复尝试，但收益要沿具体行为核验：代码组的 5 个目标错误，在原轨迹后段都已经自行修复；指导避免了重犯，其中 4 条仍出现其他参数错误。语义组补好了部分公式和字段，也留下了筛选与余额口径问题。

另一个影响读数的因素是问题匹配：同一缺陷可能被三轮 Judge 写成不同描述，拆成单票后漏计。因此表中的小幅分差不作为稳定提质的证据；更少的生成 token 也需与功能保留一起检查。

Offline：沿依赖关系编辑

Offline 的处理对象是一条已有的完整轨迹。先确定修改会影响哪些资源状态、返回值、控制条件和文字上下文，再选择单 turn 编辑、有限片段编辑或不编辑。四类依赖可以重叠；需要真实执行的问题回流 Online，未知依赖或其他准出失败进入 Pending。

例如，删除一个无副作用的失败调用后，后文的“刚才失败，所以重试”也需要重写；若修改字段创建参数，后续使用的字段 ID、公式和视图也可能受影响。动作变化必须有相应的真实执行证据，不能把失败回执改成成功。清洗同样保留信息时序，不把事后知道的结论提前写入决策。

GPT-5.6 Luna xhigh：两个修前 / 修后配对，加一个未修改原轨迹，共 15 次有效评审。问题计数的变化涉及未修改事实的票数波动，不能直接解释为修好或引入了问题。

当前样本主要覆盖文字与简单控制依赖。构造反例进一步发现，换一种说法引用已删除的失败、提前声称未来操作成功，仍可能绕过校验。资源状态和返回值传播将是后续测试的重点。

从轨迹到训练样本

当前准出规则按问题多数票计算分档：有严重问题为 2 分，仅轻微问题为 3 分，无问题为 4 分；无问题且至少两轮效率评审为 high 时为 5 分。4/5 分轨迹再通过真实性与格式检查。评分、产物验收和训练格式承担不同检查职责。

一批已提交训练的数据包含 207 条轨迹、206 个 Query 组，按 Query 分组拆为 186 条训练与 21 条独立测试。训练侧展开为 5,458 个 assistant 目标：每个目标保留完整、未截断的历史上下文，原生思考只保留当前目标轮。测试数据不提交训练或选 checkpoint。

新一轮在线对照从同一 Query 各自 fresh 生成：普通生成，对比教师纠偏及后验修复，先检查 10 对再扩到 100 对。这样可以把重新生成本身的收益，与修复机制的收益分开。接下来的判断标准是：同一需求上的功能保留、可用轨迹比例，以及包含教师和 Judge 的完整成本。

方案设计：Spec → TodoList

规划工具与普通执行工具共用 Harness 的调用、回执与记录机制。执行返回推动 TodoList 状态更新；Judge–Fix 的归因推动计划修订。需要重新执行的修改进入 Online；已有轨迹中可验证的局部修改按 Offline 处理。TodoList 的完成标记始终要能追到真实动作与回执。

Spec 提供业务对象、约束和依赖，TodoList 将其组织成可更新的执行计划。规划工具维护任务顺序、完成状态和执行依据，让计划随真实工具返回更新。这是本方案采用的规划结构；前面的三组实验比较的是 Spec 的输入位置。

Judge–Fix 将同时检查计划、实际动作及二者的一致性。例如，工作流依赖的字段尚未建立，就修正 TodoList 的前置任务和执行顺序，并重新生成受影响的执行片段。保留计划修订、工具调用与真实回执，经核验后形成显式规划与执行的训练数据。

验收仍以原始 Query 为准。模型生成的 Spec 和 TodoList 保留为可修订的计划及过程证据，不新增用户要求；完成标记需要对应实际执行。对照实验将比较有无 TodoList 时的任务完成率、依赖与顺序错误、可用轨迹比例及完整成本。这条设计的收益待后续实验验证。

本文整理自 2026 年 10 月的 CLI 轨迹合成与修复实验。三组 Spec 对照、定向续跑和局部编辑使用各自的固定样本与评审协议，分别报告。
